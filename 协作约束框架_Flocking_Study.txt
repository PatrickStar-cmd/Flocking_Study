Flocking_Study 三人协作与研究管理约束框架
版本：v1.0
适用仓库：PatrickStar-cmd/Flocking_Study
用途：约束三名成员及后续 AI 协作者的代码、实验、结果、论文和 Git 协作行为

一、项目定位

本仓库用于管理无人集群、Allocentric Flocking、有效社会输入、间歇方位观测、连续遮挡、距离相关输入以及方位预测补偿相关的科研代码、实验结果、研究记录和论文材料。

当前主研究因素：
1. 邻居数量 k；
2. 邻居方位角结构；
3. 连续遮挡时间 T；
4. 距离相关输入幅度作为现实感知扩展。

仓库中的任何修改都必须同时考虑：
1. 软件是否可运行；
2. 实验是否可复现；
3. 结果是否可追溯；
4. 统计结论是否超出证据；
5. 论文表述是否与实际实现一致。

二、仓库结构与文件边界

1. allocentric-flocking-original/
   - 原始 MATLAB 对照代码。
   - 只读，任何人不得直接修改、重命名、删除或格式化。
   - 如需扩展，必须在 effective-social-input/ 中建立独立实现。

2. effective-social-input/
   - 当前主要研究目录。
   - 包含 MATLAB 仿真器、运行器、测试、绘图脚本、Python 分析工具和研究文档。
   - 代码修改必须通过独立分支完成。

3. effective-social-input/results/
   - 保存历史实验、CSV、MAT、日志、图表和审计信息。
   - 已有结果默认只读，禁止覆盖、重命名、删除或用新结果替换旧结果。
   - 新实验必须使用新目录或明确的新文件名。

4. effective-social-input/AGENTS.md
   - 当前目录的优先工作说明和研究状态修正。

5. effective-social-input/AGENT_WORK_PROTOCOL.md
   - 实验、代码、统计和提交的工作协议。

6. effective-social-input/RESEARCH_ROADMAP.md
   - 研究阶段、验收标准和论文主线。

7. effective-social-input/*STATUS.md、*PLAN.md
   - 当前实现状态、实验计划和未完成事项。
   - 不得把计划内容写成已完成结果。

8. paper/
   - LaTeX、PDF 和论文草稿。
   - 论文中的结论必须能够追溯到代码、结果和统计分析。

9. 根目录 README.md、初稿问题检查与重写清单.md
   - 项目总览和论文审计依据。

三、Git 分支体系

推荐建立以下长期分支：

1. main
   - 稳定、可复现、可对外展示的版本。
   - 禁止直接 push。
   - 只能通过 Pull Request 合并。

2. develop
   - 三人日常集成分支。
   - 可以包含已完成基本测试但尚未作为最终版本发布的内容。
   - 禁止直接覆盖他人提交。

3. 任务分支
   - feature/<name>：功能开发。
   - exp/<name>：实验、参数扫描和分析。
   - paper/<name>：论文或图表修改。
   - docs/<name>：协议、README、研究路线和状态文档。
   - hotfix/<name>：紧急缺陷修复。

推荐流程：

任务分支 -> Pull Request -> develop -> 审查与测试 -> Pull Request -> main

如果暂时没有 develop，则使用：

任务分支 -> Pull Request -> main

但不得直接在 main 上进行日常开发。

四、分支和工作区规则

1. 每个任务只能对应一个明确的任务分支。
2. 分支名称必须说明任务目的，不使用 test、new、final、final2、最新等模糊名称。
3. 开始工作前必须检查：
   - 当前分支；
   - git status；
   - 最近提交；
   - 目标分支是否有新提交；
   - 是否存在未提交的他人修改。
4. 开始工作后不得直接覆盖未提交文件。
5. 不得使用 git reset --hard、强制推送或无确认的批量删除。
6. 需要同步目标分支时，优先使用普通 merge 或经确认的 rebase。
7. 发现冲突时先保留双方版本，分析冲突语义后再处理。
8. 不得通过删除文件、改名或覆盖结果来隐藏冲突。
9. 每项任务完成后必须检查 git diff 和 git status。
10. 每次合并必须保留可追溯的提交历史。

五、三人协作规则

1. 任何成员都可以提交新改动，但必须使用自己的任务分支。
2. 一个人的提交不能直接写入另一个人的工作分支。
3. 修改同一文件前，尽量在任务说明中登记文件范围。
4. 修改同一文件的同一区域时，必须先沟通或建立明确的先后顺序。
5. 代码、实验、论文和文档可以并行，但必须在 Pull Request 中说明相互依赖。
6. 如果一项实验依赖尚未合并的代码，必须明确写出依赖分支和提交号。
7. 如果一个人的新结果依赖另一个人的旧结果，必须记录源结果目录和哈希。
8. 研究口径发生冲突时，以 AGENTS.md、工作协议和路线图为准；如果仍无法判断，暂停合并并由三人共同决定。
9. 不得因为“看起来更好”而单方面修改阈值、成功定义、种子范围或排除规则。
10. 所有重要决策都应写入文档或 Pull Request，而不是只留在聊天记录中。

六、文件和结果保护规则

1. 原始代码目录永远只读。
2. 历史 CSV、MAT、PNG、PDF、日志和 audit 文件默认只读。
3. 新实验不覆盖旧实验。
4. 设计变化、参数变化、种子变化、代码变化或统计定义变化，都应创建新版本目录。
5. 新实验目录建议包含：
   - README.md；
   - metadata.json；
   - audit.json；
   - summary.csv；
   - 日志；
   - 图表；
   - 必要的独立复核脚本或复核说明。
6. 结果目录命名必须体现实验主题和版本，例如：
   - results/distance-weight-pilot-v2/
   - results/occlusion-t30-seed101-150/
   - results/time-series-validation-20260920/
7. 运行失败时保留日志和部分结果，不得删除失败痕迹。
8. 不能把新的统计分析直接写回旧 CSV；应生成新的分析输出。
9. 大规模本地临时文件可由 .gitignore 排除，但必须保留重新生成所需的脚本和参数。
10. 任何删除实验结果的操作都必须获得三人明确同意，并优先采用可恢复移动或新提交反向撤销。

七、实验设计与科研证据规则

1. 每项实验开始前必须写明：
   - 研究问题；
   - 输入代码和提交号；
   - 参数；
   - 随机种子；
   - 样本量；
   - 输出字段；
   - 成功定义；
   - 统计方法；
   - 验收标准；
   - 证据类型。
2. 证据类型必须标注为：软件测试、探索性实验、开发集评估、独立验证或确认性实验。
3. 同一批数据既用于阈值标定又用于性能评估时，必须明确标为探索性分析。
4. 不得把 k=7、k=10 或其他单点估计写成普适邻居下限。
5. fixed-total 只用于拆分输入强度和角度结构效应，不得作为默认生物机制或真实无人机控制律。
6. 只有方位观测时，不得声称恢复了二维邻居位置。
7. 不得把时间平均指标重新命名为持续成功、失效时间、恢复时间或安全保证。
8. 不得把普通 KF 写成自动抗离群、自动恢复真实位置或具有闭环稳定性证明。
9. 预测收益必须同时报告预测错误代价、协方差失配和失效边界。
10. 遮挡期间控制器不得访问隐藏目标的真实位置、真实方位、真实速度或真实距离。
11. 近邻、远邻、方位结构和遮挡时长必须分层记录，不能混成一个不可解释因素。
12. 不得通过选择高 GO 终点、成功种子或有利检查点制造策略差异。
13. 发现非单调曲线时必须保留原始曲线，不得只展示平滑后结果。
14. 95% Wilson 下界未达到 0.95 时，应写“尚未证明达到 0.95”，不能简单写成“失败”。

八、代码修改规则

1. 修改前先说明修改目标、影响范围和验收标准。
2. 保持旧 summary 字段兼容；新增字段不得无理由删除旧字段。
3. 新随机过程必须记录随机种子和参数。
4. 不改变随机数调用顺序，除非任务明确要求并记录影响。
5. 修改仿真器后必须运行最小 smoke test。
6. 修改滤波器、遮挡或观测模块后必须运行相关契约测试和边界测试。
7. 修改分析脚本后必须独立复算至少一个关键计数或均值。
8. 修改绘图脚本后必须确认图中参数、单位、样本量和图例正确。
9. 不得把接口接通、代码运行成功或单元测试通过写成科学收益已经得到证明。
10. 代码注释应说明模型假设、可观测性限制和不能做出的结论。

九、论文修改规则

1. 论文结论必须能追溯到具体实验目录、脚本、参数和统计结果。
2. 论文中必须区分：模型定义、实验设计、软件验证、探索性结果和确认性证据。
3. 不得把计划、候选方案或未运行的实验写成已完成工作。
4. 不得将局部 KF 性质直接写成整体闭环稳定性证明。
5. CBF 表述必须核对相对阶数、估计误差、输入饱和、QP 可行性和松弛机制。
6. 低通信场景中的每个量必须说明来源：本机传感器、邻居广播、缓存、估计值或仿真真值。
7. 遮挡必须区分缺失、延迟、噪声、视场限制和数据关联错误。
8. 只有在存在完整证据时，才能使用“稳定性保证”“安全保证”“普适”“完全抵消”等强表述。
9. 论文图表必须能够由仓库中的脚本从原始结果重建。
10. 修改论文强结论时，应同步检查摘要、引言、方法、结果、讨论和结论。

十三、代码和实验审查提示词

请只读审查本次修改，不要直接修改文件。

审查以下内容：
1. 是否修改了 allocentric-flocking-original/；
2. 是否覆盖了历史结果；
3. 是否违反 AGENTS.md、AGENT_WORK_PROTOCOL.md 或 RESEARCH_ROADMAP.md；
4. 是否记录了参数、种子、代码提交号和软件版本；
5. 是否区分探索性和确认性证据；
6. 是否混淆方位观测与二维位置可观测性；
7. 是否把 KF、接口接通或单次轨迹误写成预测收益或安全保证；
8. 是否破坏旧字段、旧接口或已有测试；
9. 是否存在数据泄漏、样本重复或事后选种子；
10. 是否能用 git revert 安全回退。

请按以下格式输出：
- 结论：可以合并 / 需要修改 / 阻塞；
- 必须修复的问题；
- 建议修复的问题；
- 对历史结果的影响；
- 对论文结论的影响；
- 已验证的测试；
- 尚未验证的风险；
- 推荐的回退方式。

十五、合并与回退规则

1. 合并到 develop：表示进入共同开发线，不代表最终结论成立。
2. 合并到 main：表示该版本经过审查，适合作为稳定版本保存。
3. 合并前必须确认目标分支没有新的冲突提交。
4. 合并后发现代码或结论错误，优先使用 git revert，不删除历史。
5. 尚未共享的本地提交可以在确认后回退；已经推送或被他人使用的提交不得重写公共历史。
6. 回退操作必须说明：
   - 回退的提交；
   - 回退原因；
   - 受影响文件；
   - 是否影响实验结果；
   - 是否需要重新运行实验；
   - 如何恢复被回退内容。
7. 回退代码不等于回退外部传播的结论；如果结果已经进入论文或报告，必须同步修订相关文档。

十七、最终原则

1. 任何人都可以提交，但任何人都不能直接覆盖别人。
2. 所有修改都必须可追溯、可审查、可回退。
3. 所有结果都必须可复现、可解释、可区分证据等级。
4. 稳定主分支优先于快速合并。
5. 历史结果优先保留，新的观点通过新实验和新文档表达。
6. 软件运行成功不等于科研结论成立。
7. 代码、数据、统计和论文必须形成一致的证据链。
8. 遇到冲突时，保留信息、停止覆盖、公开差异、共同决策。
